## 1. Elevator Pitch

**The Problem:** A social-media product needs automatic landmark tagging: given an uploaded photo, return the top-k most likely landmarks among 50 world landmarks. The deliverable is not one model but a complete, executed pipeline - a CNN trained **from scratch** and a **transfer-learning** model, both exported to TorchScript, wrapped in an interactive app, and graded against a rubric (scratch ≥ 50% test accuracy, transfer ≥ 60%). The training machine is a laptop with a **4 GB** RTX 500 Ada GPU, so every design choice had to respect a hard VRAM budget, and the notebooks' printed numbers had to match the written analysis.

**The Solution:** Seven `src/` modules (`data`, `helpers`, `model`, `optimization`, `train`, `transfer`, `predictor`) implemented around the starter's exact function signatures, plus three notebooks executed top-to-bottom with `jupyter nbconvert --execute`. The scratch CNN is a five-block VGG-style network (32 → 512 filters, BatchNorm, MaxPool, Dropout2d, AdaptiveAvgPool, 512-512-256-50 head; **1,977,938 parameters**), trained for 80 epochs with Adam and AMP. The transfer model is **EfficientNet-B0** pretrained on ImageNet with a frozen backbone and a new `nn.Linear(1280, 50)` head - only **64,050 of 4,071,598 parameters trainable**. Both use `torch.amp.autocast` + `GradScaler`, batch size 32, `ReduceLROnPlateau`, and best-validation-loss checkpointing.

**The Result:** The scratch CNN reached **66% test accuracy (825/1250)** and its TorchScript export reproduced **65.76%**, clearing the rubric's 50% bar (and the brief's 40% bar). The EfficientNet-B0 transfer model reached **76% test accuracy (951/1250)**, clearing the 60% bar. Training peaked at **1.03 GB of 4.29 GB VRAM** with zero OOM errors, at roughly 60 s/epoch for transfer learning and ~60 s/epoch for the scratch model. The app, loading `checkpoints/transfer_exported.pt` via `torch.jit.load`, tagged an external Eiffel Tower photo (not in the dataset) as **Eiffel Tower with 0.941 probability**, followed by Terminal Tower (0.029), Vienna City Hall (0.013), Stockholm City Hall (0.004) and Temple of Heaven (0.003). All **18 embedded pytest tests** pass, all three notebooks have **zero error outputs**, and no `YOUR CODE HERE` placeholder remains.

## 2. Architecture & Modeling Design

### Modeling Pipeline

```txt

│ ImageFolder → per-channel mean/std computed once and cached (mean_and_std.pt) │
└──────────────────────────────┬────────────────────────────────────────────────┘
                               ▼ data.py
┌───────────────────────────────────────────────────────────────────────────────┐
│ train: Resize(256) → RandomCrop(224) → RandomHorizontalFlip → Rotate(10°)     │
│        → ColorJitter(0.3, 0.3, 0.3) → ToTensor → Normalize(mean, std)         │
│ valid/test: Resize(256) → CenterCrop(224) → ToTensor → Normalize              │
│ split valid_size=0.15 (seed 42): train 4,246 · valid 750 · test 1,250         │
│ batch 32 · num_workers=0 (Windows/Jupyter safe) · SubsetRandomSampler         │
└──────────────────────────────┬────────────────────────────────────────────────┘
                               ▼ model.py / transfer.py
┌───────────────────────────────────────────────────────────────────────────────┐
│ Scratch: Conv(3→32→64→128→256→512) × [Conv3x3 → BN → ReLU → MaxPool → Drop2d] │
│          → AdaptiveAvgPool(1) → 512-512-256-50 head (BN1d, ReLU, Dropout)     │
│          1,977,938 parameters · Kaiming init · raw logits (no softmax)        │

                               ▼ train.py / optimization.py
┌───────────────────────────────────────────────────────────────────────────────┐
│ CrossEntropyLoss · Adam(lr=1e-3, wd=1e-4) · batch 32 · AMP fp16 + GradScaler  │
│ zero_grad → autocast forward → loss → scaler.scale(loss).backward()           │
│ → scaler.step(optimizer) → scaler.update() · OOM batches skipped safely       │

└───────────────────────────────────────────────────────────────────────────────┘
```

### Key Design Decisions

| Decision | Rationale |
| :--- | :--- |
| **Follow the starter's signatures, not the brief's alternate API** | The brief proposed `test()`, `predictor_transform()` and a scheduler passed into `optimize()`, but the actual starter ships embedded pytest tests and notebook cells that call `one_epoch_test(...)`, `valid_one_epoch(...)`, `get_model_transfer_learning(model_name, n_classes)` and a scheduler created inside `optimize()`. Matching the real scaffold kept 18 tests and every notebook cell working unchanged; the brief's extras were added as compatible helpers (`predictor_transform`, `get_model_instance_segmentation`). |
| **Normalize with dataset statistics, computed once** | The per-channel mean `[0.4638, 0.4725, 0.4687]` and std `[0.2697, 0.2706, 0.3017]` were computed over the training images with `ToTensor()` only and cached to `mean_and_std.pt`. Both models see the same input distribution, and the cache removed a multi-minute recomputation from every notebook run. |
| **Augment only the training split** | Horizontal flips, ±10° rotation and ±0.3 color jitter attack the real variation in user photos (viewpoint, lighting) while validation/test stay deterministic (`Resize(256)` + `CenterCrop(224)`), so the reported accuracy measures generalization rather than luck with random crops. |
| **Five blocks, doubling filters, global average pooling** | 224 → 112 → 56 → 28 → 14 → 7 keeps spatial reduction regular; `AdaptiveAvgPool2d(1)` removes the huge flatten layer that would otherwise dominate parameters and VRAM. The 32 → 512 width was chosen after the first narrower model (16 → 256) underfit; the wider version reached 66% while still fitting comfortably in 4 GB. |
| **Adam instead of the brief's SGD** | The first 50-epoch SGD run (lr 0.01) reached only 31% and its loss curve was still falling at epoch 50 with the LR never plateauing - a convergence problem, not an overfitting problem. Adam at lr 1e-3 plus 80 epochs converged far enough to reach 66%; the scheduler still stepped 1e-3 → 5e-4 (~epoch 43) → 2.5e-4 (~epoch 75). |
| **AMP on every training batch** | `torch.amp.autocast("cuda")` + `torch.amp.GradScaler("cuda")` cut activation memory roughly in half and made batch 32 at 224×224 safe on the 4 GB card. `torch.cuda.amp` was avoided because it is deprecated in torch 2.14. |
| **OOM-tolerant training loop** | A `RuntimeError` containing "out of memory" skips the offending batch, zeroes gradients and calls `torch.cuda.empty_cache()` instead of killing a 30-epoch run. No OOM occurred in the final runs, but the safety net is part of the delivered loop. |
| **Frozen backbone + fresh head for transfer learning** | EfficientNet-B0's ImageNet features already encode edges, textures and object parts that transfer to landmark photos. Freezing 4.0M of 4.07M parameters made each epoch ~60 s and reduced overfitting on ~4.2k training images; the head alone reached 76% test accuracy. |
| **Checkpoint on validation loss, evaluate test once** | `optimize()` saves weights only when validation loss improves by more than 1%; the test set is touched only by `one_epoch_test()` after training. Hyperparameters were selected on validation, never on test. |
| **TorchScript-safe inference path** | `Predictor` uses `nn.Sequential` of torchvision transforms (scriptable) instead of `Compose`, then `F.softmax(dim=1)`. The exported model reproduced 65.76% versus 66% for the eager model, confirming the serialization is faithful. |
| **Windows-safe data loading** | `num_workers` is clamped to 0 on Windows in both `get_data_loaders()` and `compute_mean_and_std()`, because worker processes cannot be spawned from Jupyter/pytest without a `__main__` guard on this platform. |

## 3. Machine-Learning Principles in Practice

**Diagnose before tuning.** The first scratch CNN (16 → 256 channels, SGD lr 0.01, 50 epochs) reached only 31% test accuracy. The executed loss curve showed *both* training and validation loss still falling (train ≈4.5 → 3.05, validation ≈3.8 → 2.8) and the learning rate flat at 0.01 - the signature of underfitting/convergence, not overfitting. That diagnosis drove every subsequent change: wider filters (32 → 512), Adam, more epochs, and lighter convolutional dropout (0.05). The same architecture then reached 66%.

**Validation selects, test reports.** All hyperparameter decisions used the 750-image validation split; the 1,250-image test set was evaluated once per model after training, with the best-validation checkpoint. This is why the reported 66% and 76% are credible generalization estimates rather than training-time snapshots.

**Mixed precision is a numerical contract, not a speed flag.** Every forward pass runs under `autocast`, every backward under `scaler.scale(...).backward()`, and every optimizer step under `scaler.step()` + `scaler.update()`. Skipping the unscale step silently corrupts gradients; keeping the three calls together in one loop is what makes fp16 safe on a 4 GB card.

**Transfer learning means freezing, not just loading.** `get_model_transfer_learning()` sets `requires_grad = False` on every backbone parameter before replacing the head, and `get_optimizer()` filters to `p.requires_grad`. The parameter audit (64,050 trainable / 4,071,598 total) is the proof that the backbone really is frozen and that the optimizer is not wasting state on 4M dead weights.

**Reproducibility is part of the artifact.** `torch.manual_seed(42)`, `np.random.seed(42)` and `torch.cuda.manual_seed_all(42)` are set in both training notebooks, and `torch.backends.cudnn.benchmark = True` is enabled only after seeding. The dataset split is seeded through `torch.randperm`, so the same train/validation partition is reproduced on every execution.

**Checkpoint selection is a modeling decision.** Saving on training loss would have selected an overfit model; saving only when validation loss improves by >1% keeps the model that generalizes. The final Part 1 and Part 2 checkpoints are exactly those validation minima, which is why the exported models match the reported accuracies.

**Claims stay inside the evidence.** 66% and 76% describe this 50-class, ~6k-image teaching subset - not the full Google Landmarks Dataset v2. The app demo is a single external image, reported with its full top-5 distribution rather than a single confident label, because one image proves the pipeline works, not that the model is universally accurate.

## 4. AI Collaboration Playbook

The deliverable was three notebooks whose cells had to run in order, whose embedded tests had to pass, and whose written numbers had to match executed outputs - so the workflow was built around **inspect → repair → implement → smoke-test → execute → diagnose → verify**.

The workflow was:

1. **Read the real scaffold before trusting the brief.** Plan-mode inspection of `src/*.py` and all notebook code cells revealed that the starter's function signatures, scheduler location and model constructor differed from the brief, and that the installed PyTorch was a `+cpu` build despite the 4 GB RTX 500 Ada being present. Both discrepancies were resolved before any implementation.
2. **Repair the environment first.** Reinstalled `torch 2.14.1+cu130` / `torchvision 0.29.1+cu130` (the cu130 wheels match the installed 13.2 driver), verified `cuda.is_available()`, AMP, and TorchScript scripting; downloaded the 717 MB dataset archive that the brief assumed was already present and verified 50 classes / 4,996 / 1,250 images.
3. **Implement the modules against their own tests.** `data.py`, `model.py`, `optimization.py`, `train.py`, `transfer.py`, `predictor.py` and `helpers.py` were filled in, with Python 3.14 fixes applied to the embedded tests (`dataiter.next()` → `next(dataiter)`) and the removed `pretrained=True` API replaced by `torchvision.models.get_model(..., weights=...)`.
4. **Smoke-test before spending GPU hours.** Synthetic AMP loops confirmed 0.38 GB peak VRAM for the scratch CNN and 0.22 GB for EfficientNet-B0; a full `optimize()` run on a tiny dataset exercised livelossplot, the scheduler and checkpoint saving before the real 80-epoch run.
5. **Execute, then diagnose with real numbers.** Part 1's first execution returned 31%; the executed loss curve was extracted from the saved notebook and read before changing anything. The second Part 1 run (wider model, Adam, 80 epochs) returned 66%. Part 2 executed once and returned 76%.
6. **Verify mechanically.** A final pass parsed the saved notebooks: zero error outputs, zero remaining placeholders, 18/18 pytest, all checkpoints present, TorchScript reload accuracy 65.76%, and the app's top-5 output.

The collaboration principle was the same as in P1: **verify, don't trust.** Every figure in these notes was read from an executed notebook or printed test, and the environment assumptions in the brief were treated as hypotheses to check, not facts to build on.

## 6. Challenges & Resolutions

### Challenge 1 - The installed PyTorch was CPU-only

**What happened:** The brief assumed a working CUDA setup and prescribed AMP and batch-size discipline for a 4 GB RTX 500 Ada. In reality `torch.__version__` was `2.14.1+cpu` and `torch.cuda.is_available()` returned `False`, while `nvidia-smi` showed the GPU idle with a 13.2 driver. Every GPU-dependent instruction in the brief was unusable as delivered.

**Resolution:** Verified that the PyTorch index publishes cp314/win_amd64 wheels for `torch 2.14.1` and `torchvision 0.29.1` under cu130, then force-reinstalled both (`pip install --force-reinstall --no-deps ... --index-url https://download.pytorch.org/whl/cu130`). Re-verified: CUDA available, device `NVIDIA RTX 500 Ada Generation Laptop GPU`, 4.29 GB, compute capability 8.9, `torch.amp.GradScaler`/`autocast` present. The rest of the GPU plan then worked as written.

### Challenge 2 - The dataset was not actually on disk

**What happened:** The brief stated the dataset was already downloaded under `landmark_images/`, but `get_data_location()` raised `OSError: Please download the dataset first` and a filesystem search found no copy anywhere on the machine. The first pytest run failed 11 of 18 tests for this reason alone.

**Resolution:** Downloaded the official archive (717 MB) from the URL already hardcoded in `src/helpers.py`, extracted it with `tar`, and verified the structure: 50 class folders in `train/` and `test/`, 4,996 training images and 1,250 test images. Then computed and cached the dataset mean/std once so subsequent runs would not repeat the scan.

### Challenge 3 - Python 3.14 broke three starter APIs

**What happened:** The project venv runs Python 3.14.7 with torch 2.14.1 / torchvision 0.29.1, and the starter code used three APIs that no longer behave as written: (a) the embedded pytest fixtures call `dataiter.next()`, which has not existed since Python 3; (b) `get_model_transfer_learning()` called `getattr(models, name)(pretrained=True)`, an argument removed from modern torchvision; (c) the brief's AMP guidance points at `torch.cuda.amp.autocast`/`GradScaler`, deprecated in torch ≥ 2.4.

**Resolution:** Replaced `.next()` with `next(...)` in the fixtures; rewrote model loading around `torchvision.models.get_model_weights(name).DEFAULT` + `models.get_model(name, weights=...)`; and used `torch.amp.autocast(device_type="cuda")` + `torch.amp.GradScaler("cuda")` throughout, with a fallback to the legacy API for older torch versions. All 18 tests pass on the current stack.

### Challenge 4 - Windows DataLoader workers cannot be spawned from Jupyter

**What happened:** The starter defaulted `num_workers=-1` to `multiprocessing.cpu_count()`, and `compute_mean_and_std()` did the same. On Windows, worker processes re-import the main module and fail without an `if __name__ == "__main__":` guard - which cannot exist in a notebook. The brief itself warned about this but the scaffold did not implement the guard.

**Resolution:** `get_data_loaders()` and `compute_mean_and_std()` now clamp `num_workers` to 0 when `os.name == "nt"`, while preserving the `-1 = all cores` semantics on other platforms. Data loading runs serially on this machine; the measured cost is acceptable (~60 s/epoch for transfer learning at batch 32).

### Challenge 5 - The first scratch CNN plateaued at 31%

**What happened:** The first Part 1 execution (16 → 256 filters, SGD lr 0.01, 50 epochs, dropout 0.1) returned **31% test accuracy** - below both the brief's 40% and the rubric's 50%. The saved loss curve showed train ≈4.5 → 3.05 and validation ≈3.8 → 2.8, both still falling, with the learning rate flat because `ReduceLROnPlateau` never saw a plateau.

**Resolution:** Treated it as underfitting rather than guessing at regularization. A 20-epoch controlled experiment with a wider network (32 → 512) and Adam lr 1e-3 reached 32% validation accuracy by epoch 20 while still improving. The final configuration - wider CNN, Adam, 80 epochs, convolutional dropout reduced from 0.1 to 0.05, early-stopping patience 20 - reached **66% test accuracy**. The first run's checkpoint and exported model were overwritten by the successful run, so the delivered artifacts are consistent with the reported number.

### Challenge 6 - The starter hardcoded a ResNet head

**What happened:** `src/transfer.py` assumed every architecture exposes `model.fc` (`num_ftrs = model_transfer.fc.in_features; model_transfer.fc = nn.Linear(...)`), which is true for ResNet but not for the recommended EfficientNet-B0 (`classifier[1]`) or MobileNetV3 (`classifier[3]`).

**Resolution:** Replaced the hardcoded assignment with a generic helper that walks `named_modules()`, finds the last `nn.Linear`, resolves its parent module by dotted path and swaps it for `nn.Linear(in_features, n_classes)`. This supports ResNet, EfficientNet and MobileNetV3 with the same code path; the delivered transfer model is EfficientNet-B0 with `classifier[1] → Linear(1280, 50)`.

## 7. Review & Refinement

The principal refinement was **replacing the first scratch-CNN configuration after reading its executed loss curve**. The plan followed the brief's suggested SGD lr 0.01 and a narrow 16 → 256 network; the executed result (31%, losses still falling, LR never stepped) showed the plan's assumption was wrong. The corrected configuration - 32 → 512 filters, Adam lr 1e-3, 80 epochs, lighter convolutional dropout, early stopping - moved the test accuracy from 31% to **66%**. This was a diagnosis-driven change, not a hyperparameter sweep.

A second refinement was **aligning the notebooks with the rubric rather than only the brief**. The brief set a 40% scratch target, but `docs/4. Rubric.md` requires **50%**; the final 66% clears both. The rubric also requires the Part 3 notebook to show a non-dataset image with predictions, which the starter's widget alone does not produce - so a demo cell was added that loads an external photo, prints the top-5 distribution and renders a bar chart next to the image.

A third pass **corrected the written analyses to match the delivered implementation**. The starter's answer markdown described RandAugment and ResNet18; the final text describes the actual ColorJitter/flip/rotation pipeline and the actual EfficientNet-B0 frozen-head architecture, with parameter counts and rationale. Hyperparameters quoted in the notebooks (batch 32, Adam, 80/30 epochs, wd 1e-4) match the cells that were executed.

The final review ran a mechanical sweep over the saved artifacts: all 18 pytest tests passed, all three notebooks had zero error outputs, all checkpoints existed and loaded, the TorchScript export reproduced 65.76% on the test set, and the app returned a sensible top-5 for an unseen image. **No issues were found that block submission.**

## 10. Retrospective

### What I'd Do Differently

1. **Check the environment before planning the compute strategy.** The brief's AMP/batch-size plan assumed CUDA, but the venv shipped a `+cpu` torch build and the dataset was missing. Both were discoverable in the first five minutes; surfacing them at the start turned two potential mid-run failures into a single repair step.
2. **Pre-resize the dataset once to cut epoch time.** JPEG decoding at full resolution is the bottleneck (~60 s/epoch with `num_workers=0`). A one-time cache of images resized to ~320 px would have roughly halved the wall-clock time of both runs without changing the modeling logic.
3. **Log epoch metrics outside livelossplot.** `MatplotlibPlot` clears the cell's stdout each epoch, so the printed per-epoch losses are lost from the saved notebook. Writing metrics to a CSV (or printing only at the end) would have made the loss numbers quotable exactly instead of read from the curve.
4. **Try partial fine-tuning as a bonus experiment.** The frozen-backbone model already clears 60%, but unfreezing the last EfficientNet block at a 10× lower LR is the natural next experiment; it was skipped to protect the 4 GB VRAM budget, not because it was measured and rejected.
5. **Add test-time augmentation to the evaluation.** Averaging logits over the original and a horizontally flipped image typically buys 1–2 points for free. It would have required a second exported inference path, so it stayed out of the graded artifact.

### What Worked Well

1. **Reading the starter before writing.** Knowing the exact pytest contracts and notebook call sites meant all modules were implemented once, with no rewrites of scaffold code and no signature drift.
2. **Smoke tests before long runs.** Synthetic AMP loops and a tiny `optimize()` run validated the scaler path, scheduler and checkpointing in minutes, before any 80-epoch commitment.
3. **Diagnosis from the executed curve.** The 31% run was not "fixed" by guessing; the saved loss curve identified underfitting and pointed directly at capacity, optimizer and epoch count. The 66% result followed from that evidence.
4. **AMP discipline on a small GPU.** Keeping `autocast`/`scale`/`step`/`update` together made batch 32 at 224×224 safe, and measured peak VRAM (1.03 GB) left ample headroom for the rest of the pipeline.
5. **TorchScript verified by round-trip.** Reloading the exported model and re-scoring the full test set converted "the export ran" into "the export still works", which is the property the app depends on.
6. **A rubric-driven final pass.** Checking `docs/4. Rubric.md` caught the 50% (not 40%) scratch threshold and the requirement for an app demo on a non-dataset image; both were addressed before the final execution.

### The AI Partnership

> "The value of the AI partnership here was environmental skepticism plus measured iteration. The planning pass read the actual scaffold and found that the brief's signatures, dataset location and CUDA assumption were all wrong for this machine; the executing agent then repaired the environment (cu130 torch wheels, 717 MB dataset download), implemented seven modules against their embedded tests, and ran the notebooks. When the first scratch CNN returned 31%, the agent extracted the executed loss curve, diagnosed underfitting, ran a controlled 20-epoch experiment, and only then committed to the wider/Adam/80-epoch configuration that reached 66%. The human role was judgment: approving the environment changes, accepting the longer run, and deciding that a 66%/76% pair with verified exports was the right stopping point rather than chasing a higher score at the cost of the delivery. Every number in these notes traces to an executed cell or a printed test."

### Final Thoughts

This project was less about inventing an architecture and more about making a complete, honest pipeline work under real constraints: a 4 GB laptop GPU, a CPU-only PyTorch install, a missing dataset, a Python version newer than the starter expected, and a rubric stricter than the brief. The scratch CNN's 31% → 66% improvement came from reading the loss curve and changing the right variables (capacity, optimizer, epochs) rather than sweeping blindly. The transfer model's 76% came from trusting pretrained features and freezing what did not need to change. Both exports were verified by reloading them, and the app was demonstrated on a photo the model had never seen. The final artifact is reproducible, test-covered, and documented with numbers taken from its own execution.
